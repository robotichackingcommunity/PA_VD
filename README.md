# RHC Physical AI Vulnerability Database

**Where software faults meet the physical world.**

The RHC Physical AI Vulnerability Database is an open, community-driven vulnerability database focused on **Physical AI** systems - humanoid robots, industrial robots, autonomous mobile robots (AMR), drones, service robots, autonomous vehicles, and the middleware, AI models, and edge hardware that power them.

**The RHC Physical AI Vulnerability Database is not a mirror of NVD.** It takes CVEs from NVD and the CVE Program, reads the advisories each CVE record references (vendor PSIRT advisories, GitHub Security Advisories, ZDI and others) together with the matching CISA ICS advisories, and re-processes each one with domain-specific enrichment - turning a plain vulnerability advisory into actionable intelligence for robots, AMRs, humanoids, service robots, drones, industrial robots, and AV AI stacks. The approach mirrors what VicOne has already done for automotive with **AutoVulnDB**: take a generic CVE and translate it into "how does this actually get exploited on this class of physical system, and what happens in the real world when it does."

🔍 **[Browse the Vulnerability Explorer](https://robotichackingcommunity.com/physical-ai-vulnerability-database.html)** - search and filter by domain, attack surface, exploitation, severity, patch availability and publication date across the full dataset, with yearly and monthly counts.

## Why the RHC Physical AI Vulnerability Database?

Physical AI - robots, drones, autonomous vehicles, and embodied agents that perceive, decide, and act in the physical world - is being deployed at scale across manufacturing, logistics, healthcare, agriculture, and defense. Unlike traditional IT vulnerabilities, a flaw in a Physical AI stack does not just leak data - **it can cause a robot to collide, a drone to crash, a manipulator arm to injure someone, or an autonomous vehicle to misjudge the road.** That's the fault line the RHC Physical AI Vulnerability Database tracks: the point where a software bug crosses over into physical consequence.

Yet today, vulnerability intelligence for this domain is fragmented and shallow:

- **Scattered across silos** - CVE/NVD, vendor PSIRT advisories, GitHub Security Advisories, academic papers, and conference talks (DEF CON, Black Hat, S4) each hold a piece of the picture, with no unified view.
- **Missing physical-world context** - standard CVE records describe software impact (confidentiality/integrity/availability) but say nothing about the resulting physical consequence: Will the robot fall? Will the drone lose control? Will a safety interlock be bypassed?
- **No attack-surface mapping to the Physical AI stack** - a vulnerability in DDS/ROS 2 middleware, a perception model, a motion planner, or an edge AI chip (e.g. NVIDIA Jetson) requires different mitigations, but generic vulnerability feeds don't map CVEs to this architecture.
- **Hard to correlate across an ecosystem of shared components** - the same ROS 2 / DDS / PX4 / firmware vulnerability can affect dozens of unrelated robot and drone vendors that build on the same open-source or commercial building blocks, but this fan-out is invisible in vendor-specific advisories.

**The RHC Physical AI Vulnerability Database closes this gap** by re-classifying and enriching public vulnerability data specifically through a Physical AI lens: mapping every CVE to a Physical AI domain and attack surface, reconstructing plausible attack chains, and describing the physical-world consequence - so that manufacturers, researchers, red teams, and defenders can reason about robot and embodied AI security the way they already reason about IT security.

## What's Inside

Each record in [`CVE-json/`](./CVE-json) is a single vulnerability, structured in three layers plus the original CVE record:

| Section | Description |
|---|---|
| `cve_id` | The CVE identifier |
| `contributed_by` | Who produced the record: `{"source": "VicOne"}` for records generated by the project, or `{"source": "community", "github", "pull_request", "date"}` for a record added by a contributor |
| `facts` | Data taken from public sources, not written by a model: `vuln_status` (NVD), `reporter`, `references` (with tags such as vendor-advisory and patch), `affected_products`, `cvss` (NVD first, MITRE only when NVD has no score) with the CISA `ssvc` decision (exploitation, automatable, technical impact), and `epss` (FIRST) |
| `judgments.title`, `judgments.classification_reason` | A short title (vendor, product, vulnerability class and consequence) and one to three sentences on why the CVE belongs to Physical AI |
| `judgments.classification` | `domains`: each Physical AI domain (confidence of 0.7 or more; one of Humanoid & Legged Robot, Industrial Robot, Mobile Robot & AMR, Drone & Aerial Robotics, Service & Companion Robot, Autonomous Vehicle AI, Embodied AI Agent, Robot Operating Systems & Middleware, Physical AI Infrastructure) with its rationale and, **inside the domain**, its own `components` (what is affected, with a rationale) and `attack_surfaces` (Physical Layer, Perception Layer, AI Model Layer, Software & Cloud, Wireless Layer). Also `vulnerability_class` for the CVE as a whole, one `CWE-<id>: <official name>` per weakness, and `vulnerability_class_source`: `cve` when the CWE comes from the CVE record, `ai` when the record has none and the model chose it |
| `judgments.attack_scenarios` | One entry per way the flaw is attacked: a `title`, the `domains` it applies to, an `attack_chain` (preconditions and 2 to 6 conceptual steps, each marked `stated`, `inferred_from_cwe` or `assumed`, with the interface where the attack happens or enters) and an `impact` (`safety_impact` from NONE to CRITICAL and a list of `physical_world_impact` outcomes). Most CVEs have one |
| `judgments.mitigation` | Once for the CVE: whether a fix is available, the fix and any workaround |
| `mitre_data` | The complete MITRE CVE Record 5.x |

`facts` come from NVD, MITRE and FIRST. A CVE that affects several domains has its own components and interfaces for each domain. Its attack scenarios name the domains they apply to, so one attack across two domains is one scenario, and a genuinely different attack has its own attack chain and safety impact; the mitigation is written once. `judgments` are derived from the CVE text and the pages its record references, and each attack-chain step says how well it is grounded, so read `assumed` steps as general knowledge rather than something the advisory states. Attack-chain steps never contain commands or payloads.

### Updates and Removed Records

Records are re-analysed as the CVE records and the advisories they reference change, so a record can change between updates. Every update that changes the records adds a section to [`CHANGELOG.md`](./CHANGELOG.md), newest first, listing:

- the records **added**;
- the records whose **Physical AI domains** changed, with the domains before and after;
- the records whose **attack surfaces** changed within a domain, with the surfaces before and after;
- the records **removed**, split by reason.

A record is removed in two cases only:

1. **The CVE was REJECTED** by its CNA or NVD (withdrawn, a duplicate, or not a vulnerability).
2. **The CVE no longer belongs to Physical AI**: a re-analysis with newer information found no Physical AI domain that meets the confidence threshold.

A removed record's file is deleted from `CVE-json/`, and its CVE ID stays in `CHANGELOG.md`, so a reference to it can still be traced. Other edits to a record (title, CVSS, attack scenarios) are not listed; the git history of the file shows them.

### How the RHC Physical AI Vulnerability Database Differs from NVD / Generic CVE Feeds

| Dimension | NVD / generic CVE feed | RHC Physical AI Vulnerability Database |
|---|---|---|
| Technical depth | Description + CVSS score | + CISA SSVC exploitation and EPSS, a reconstructed attack path, `safety_impact`, `physical_world_impact` |
| Domain focus | Generic, no product-class context | Explicit Physical AI domains, components and attack surfaces (physical, perception, AI model, software and cloud, wireless) |
| Actionability | Reader must infer exploitation path and mitigation | Attack chain and mitigation direction are pre-written |
| Supply-chain lens | Limited | Explicitly covers companion apps, middleware (ROS 2/DDS), cloud MQTT/OTA channels, and shared component fan-out across vendors |

## Recommended Workflow

A few concrete ways to work with these records in an existing process:

1. **Design-time safety-boundary review.** Filter by `attack_surfaces` and `domains` for your product class and turn recurring patterns into architecture requirements, for example that safety-critical data must have cryptographic integrity protection and separated write privileges. Use the `attack_chain` as a starting point for a red-team scenario, then reproduce it in simulation or on hardware.
2. **Supply-chain / SBOM triage.** Filter by `affected_products` and `components` for third-party navigation controllers, ROS 2 packages, MQTT brokers, or companion apps you integrate, and prioritize by `safety_impact` and CISA `ssvc.exploitation`, not raw CVSS.
3. **Pre-deployment security testing and monitoring.** Use `attack_chain` and `attack_surfaces` to check your threat model for coverage gaps across the physical, perception, AI model, software and cloud, and wireless layers.
4. **Threat hunting and incident response.** When a new advisory shares an attack surface or weakness with an existing record, reuse its `physical_world_impact` to triage the worst case quickly. Sort by exploitation (active first) and EPSS to decide what to look at today.
5. **Academic and open-source research.** Use `attack_chain` and `physical_world_impact` as grounded, real-world case material; compare `vulnerability_class` across domains to find cross-domain patterns.
6. **Risk communication to non-technical stakeholders.** Translate "CVSS 7.3" into "this could let an AMR collide with a warehouse worker" for product, legal, insurance, and customer-facing conversations.

## Repository Structure

```
├── CVE-json/      # One <CVE-ID>.pavd.json record per CVE (the source of truth)
├── index.json     # Lightweight index (ids, severity, domains, attack surfaces, vendors, safety impact, patch availability, exploitation, EPSS)
├── stats.json     # Counts by severity / domain / attack surface / exploitation / safety impact / patch availability / publication year and month, and the latest update
├── CHANGELOG.md   # What each update added, changed (domains, attack surfaces) and removed
├── index.html     # Vulnerability Explorer: search and filter UI (GitHub Pages)
├── schema/        # pavd-record.schema.json, the schema every record must match
├── scripts/       # validate_records.py, the check run on every pull request
└── .github/       # The pull request workflow and template
```

`CVE-json/`, `index.json`, `stats.json`, `CHANGELOG.md` and the coverage block above are generated from the classification pipeline. Please do not edit them by hand.

## Contributing

Anyone can propose a new CVE record. Records must match the published schema exactly, and the maintainers review every pull request before it is merged.

**Add a new CVE: open a pull request**

1. Fork this repository and add a new file `CVE-json/<CVE-ID>.pavd.json`, for example `CVE-json/CVE-2026-10557.pavd.json`. Use an existing record as a template.
2. Set `contributed_by` to your own details. Records produced by the project carry `{"source": "VicOne"}`; yours must be:
   ```json
   "contributed_by": {"source": "community", "github": "<your GitHub account>", "pull_request": <this pull request's number>, "date": "<the day you open the pull request, YYYY-MM-DD>"}
   ```
   The check compares it with the pull request, so open the pull request first (or open it as a draft) to get the number.
3. Check it locally: `pip install jsonschema` and `python scripts/validate_records.py CVE-json/<CVE-ID>.pavd.json`. The same check runs on your pull request.
4. A pull request can only **add** files under `CVE-json/`. It cannot change or delete a record, and it cannot touch `index.json`, `stats.json`, `CHANGELOG.md`, the schema or the scripts. Pull requests that fail the check are not reviewed.

**Everything else: open an issue**

- **Change an existing record.** If you think a record is wrong (a domain, component, attack surface, safety impact or attack chain), open an issue with the CVE ID, what differs and a link to the primary source.
- **Add a field or a new allowed value.** Open an issue describing it. The schema does not change through a pull request. One exception: the component vocabulary is still being tuned, so a record may name a component that is not in the schema's `examples` list yet. Use a listed name when one fits.
- **A CVE that already exists, with different content.** Do not open a pull request. Open an issue that lists the differences.

In each case the maintainers decide whether the record is updated, so that every record stays consistent.

Please cite primary sources (NVD, vendor advisories, GitHub Security Advisories) and avoid speculative exploit details beyond what is publicly documented. Attack-chain steps must be conceptual, with no commands, payloads or exploit code.
